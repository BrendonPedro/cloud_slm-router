## 0. Which claim is being tested

The manuscript's central claim, stripped of the parts deliverables 4 and 8 already
found occupied by prior work [S: d8 §3], has three separable parts:

| ID | Claim (manuscript wording → testable form) | Source in manuscript |
|---|---|---|
| **H1** | "the intelligent router … maintains competitive response quality" while reducing cost → *a learned pre-generation router on the edge reaches a better quality/cloud-call trade-off than simple baselines* | L40, L67 (C4) |
| **H2** | the router is a "Tiny Language Model" → *a small **generative** router is needed, i.e. it beats a discriminative encoder of similar or smaller size* | L22 title, L179 |
| **H3** | collaborative inference "between Edge SLMs and Split-LLMs" → *adding a SPLIT(d) action changes the decision in a way a fixed rule cannot reproduce* | L22, L40, C2 |

The **smallest experiment** has to be able to falsify H1 and H2 cheaply, because
if either fails the paper's framing changes before any Split-LLM testbed work is
worth doing. H3 cannot be tested on quality labels alone (§6), so it is a second,
more expensive stage. Latency, throughput, cold-start and OPEX (L212–L265) are
systems measurements. They belong to Stage 2 and are **not** part of the minimum
experiment.

## 1. Why the manuscript's own data plan cannot be used as written

- The manuscript (L205) plans to use SimpleQA "with pre-computed inference results in
  LLMRouterBench", saying routing labels need not be generated by "executing every …
  pair of SLMs and Split-LLMs".
- **[M]** In the released bundle, SimpleQA (`simpleqa/test`, n = 4,326;
  `simpleqa/subset_500`) has records only for 15–17 flagship/API models (GPT-5,
  Claude-Sonnet-4, Gemini-2.5, Qwen3-235B variants, DeepSeek-V3/R1, GLM-4.6,
  Kimi-K2, Intern-S1, an `openrouter` entry). **None** of the manuscript's weak models
  (L271–L290) or strong models (L298–L302) appears there.
  (`inventory_output.txt`, last block.)
- **[M]** Of the manuscript's whole model pool, only **Meta-Llama-3.1-8B-Instruct**
  (listed as a weak model, L282) appears anywhere in the bundle. It has records on 22
  (dataset, split) pairs, none of them SimpleQA.
- Consequence: **SimpleQA routing labels for the manuscript's pool do not exist and
  must be generated by running the models.** That is a GPU job (Stage 1, §8).

## 2. What the released data *does* allow: a zero-inference Stage 0

Iteration 10 reported that only four datasets appear in both LLMRouterBench settings.
The inventory run this iteration **corrects and extends** that: flagship models also
have records on **9 performance-setting splits** that include the 7–9B pool (aime, arenahard + its three subsets, gpqa, livecodebench, livemathbench, mmlupro/test_1000; i.e. 6 distinct datasets, since the arenahard subsets appear to partition arenahard/test: 253 + 250 + 247 = 750, not checked query-by-query). On those
splits a weak (8B) model and a strong (flagship) model can be paired on the
**same queries**, matched by `origin_query` **[M]**.

is the upper bound on queries a router could "rescue" by escalating.
`weak_better` = share where the weak model scores higher. Oracle = mean of per-query max.
All values are copied from `inventory_output.txt` **[M]**.

### 2.2 What these numbers imply for the design (our analysis)

1. **With Llama-3.1-8B as the edge model, routing is almost purely "detect the easy
   queries".** `weak_better` is ≤ 0.08 on every binary split, so the oracle is barely
   above always-cloud (e.g. 0.847 vs 0.819 on MMLU-Pro). The router cannot add
   quality. It can only save cloud calls: on MMLU-Pro, 62% of queries
   (1 − need_strong) could stay on the edge with no loss against always-cloud.
   The right primary metric is therefore **cloud-call rate at matched quality**,
   not accuracy.
2. **With Qwen3-8B as the edge model the pool is complementary.** On LiveCodeBench the
   8B model beats the 235B model on 11.3% of queries and the oracle is 0.755 vs
   0.677 / 0.642. A router could in principle *raise* quality above both models.
   Qwen3-8B's released runs average ~3.7k completion tokens on MMLU-Pro, which suggests
   thinking mode was on [M: ctok column]. This is an inference, not documented.
3. **Headroom varies strongly by dataset.** This is the mechanism behind
   LLMRouterBench's own warning that routers tie simple baselines [S: d3 §4 item 8].
   It is why leave-one-dataset-out evaluation (§4) is required: a router that has
   only learned "which dataset is this" looks strong in-domain and collapses OOD.
4. **Data caveats [M: fetch-log.txt].** The `arenahard*` scores lie in {0, 0.5, 1}
   (judge win/tie/loss against a reference), not accuracy, so they are excluded from
   the primary pool. `mmlupro/test_1000` has 1,001 records but 3 duplicated query
   strings, giving 998 unique. The released `cost` field is the provider's API cost
   and says nothing about edge energy or split-link cost.

## 3. Hypotheses (pre-registered form) [P]

- **H1 (router beats simple baselines).** On held-out queries, at least one learned
  pre-generation router achieves a lower cloud-call rate at a quality level equal to
  the strong model's accuracy minus 1 percentage point than *both* (a) TF-IDF + logistic
  regression and (b) random routing at a matched call rate.
- **H2 (tiny generative router is not dominated).** The small generative router
  (option A) is **not** significantly worse than the discriminative encoder
  (option B) on the Stage-0 primary metric, **and** it offers something B does not
  (e.g. better OOD calibration). *If B ≥ A within the CI and A is slower, the "Tiny
  LM" framing (title, L179) is not supported, and the advisor options move towards
  N2 [S: d8 §4].*
- **H3 (Split action matters).** Stage 2 only; see §6.

Null for each: the difference in the primary metric has a 95% paired-bootstrap CI that
includes 0.

## 4. Dataset and splits (Stage 0) [P]

- **Primary pool:** the binary-scored splits where both the weak and strong models
  have records: `mmlupro/test_1000` (998), `gpqa/test` (198),
  `livecodebench/test` (1055), `livemathbench/test` (121), `aime/hybrid` (60).
  That is **2,432 unique queries** [M: sum of shared n above].
  AIME and LiveMathBench are too small to report on their own, so they are reported
  only in pooled results.
- **Pairs:** P-L = (Llama-3.1-8B-Instruct → qwen3-235b-a22b-2507), which uses the
  manuscript's model and is a "detect easy queries" regime; P-Q = (Qwen3-8B →
  qwen3-235b-a22b-2507), a complementary regime. The strong model is an open-weight
  model that could in principle serve as a split target. GPT-5 is run only as a
  sensitivity check.
- **In-domain split:** 60/20/20 train/dev/test, stratified by dataset and by the
  4-cell (weak correct, strong correct) outcome. Seeds {0, 1, 2, 3, 4}, and every
  number is reported as mean ± std over seeds. Query-string deduplication happens
  **before** splitting, so no query crosses splits.
- **OOD split:** leave-one-dataset-out over {MMLU-Pro, GPQA, LiveCodeBench,
  math = LiveMathBench ∪ AIME}, i.e. 4 folds. Train+dev use the other three
  groups, with dev held out at 20%.
- **Frozen before any router is trained:** split files (query hash → split) are
  written to `experiments/prototype/splits/` and hashed. The test split is opened
  once per final configuration.

## 5. Routers, baselines, metrics (Stage 0) [P]

### 5.1 Routers (from deliverable 9)

| ID | Router | Params | Output | Notes |
|---|---|---|---|---|

| A-zs | Arch-Router-1.5B as released, prompt adapted to 2 routes | 1.5B | route name | licence "other" [raw/experiment]; zero-shot, no training |
| C-pre | logistic probe on the **weak model's own** prefill hidden state | probe only | p̂ | needs the weak model's weights and one forward pass per query (GPU, Stage 1) |

C-pre is the strongest representative of option C and of prior work (ConsRoute,
RouteLMT-style in-model probes) [S: d9 §3]. It needs 8B forward passes, so in
Stage 0 it is **optional** and runs only if a GPU is available.

### 5.2 Baselines

1. always-edge; 2. always-cloud; 3. **random at matched call rate**;
4. **TF-IDF (word 1–2-gram) + logistic regression**, the "simple baseline" bar
[S: d9 §0 item 6]; 5. **dataset-prior router** (routes by dataset ID, an
information-leak control that shows how much "which benchmark" alone explains);
6. RouteLLM's released BERT classifier `routellm/bert_gpt4_augmented`, applied
zero-shot (its label is GPT-4 vs Mixtral preference, so it is a transfer baseline,
not a like-for-like one); 7. oracle (upper bound).

RouteLMT and ICL-Router (L311–L313) are **not** in the minimum experiment.
RouteLMT is an in-model probe that is covered in spirit by C-pre [S: d9 learning],
and ICL-Router needs its own training pipeline. They belong in the full paper.

### 5.3 Metrics

- **Primary:** *cloud-call rate at quality ≥ strong − 1 pt* (CCR@−1), read from the
  dev-tuned threshold and applied to test. For P-Q, also *max test quality over τ*.
- **Curve metric:** area under the quality vs cloud-call-rate curve (deferral AUC);
  RouteLLM's APGR and CPT(50%) for comparability [S: d1 §6.3].
- **Calibration:** ECE (15 bins) and Brier score of p̂; AURC for the selective
  "stay on edge" decision [S: d2 table rows 2017-05, 2017-06].
- **Router cost:** parameters, and p50/p95 router latency on the Stage-0 host
  (CPU; §7). This is measured, but it does **not** stand in for edge-device latency.

## 6. Ablations [P]

1. **Label definition:** "weak correct" vs "weak ≥ strong" vs a soft label
   (score_strong − score_weak).
2. **Router size:** B-s vs B-m, and A with 0.5B vs 1.5B (if compute allows).
3. **Input truncation:** 128 vs 512 tokens (edge latency lever).
4. **Train-set size:** 10/25/50/100% of train, to show whether the result holds with the
   ~few-hundred-label budgets that Stage 1 will have for new edge models.
5. **Jacobi variant of A (A-J):** **excluded** from the minimum experiment. The
   router emits one label token, so parallel decoding has nothing to accelerate
   [S: d6 §9; d9 §1]. It is included only if A wins H2 *and* A's output is
   multi-token.

**H3 / Split action (Stage 2, not minimum).** For a lossless partition, SPLIT(d)
and CLOUD run the same weights and give the same answer quality. So quality labels
alone cannot favour one over the other; only cost and leakage can [S: d8 §7 item 4].
Stage 2 therefore needs (i) measured activation bytes and link latency per d on the
L200 testbed, (ii) a leakage estimate per d (e.g. an embedding-inversion attack
success rate), and (iii) a sensitivity label per query. It then tests whether a
learned router beats the fixed rule "sensitive → SPLIT, else cost-optimal".
If it does not, H3 reduces to a systems policy (gap-assessment N1 precondition ii).

## 7. Statistical tests [P]

- **Paired bootstrap** (10,000 resamples of test queries, stratified by dataset)
  for the difference in CCR@−1, deferral AUC and ECE between each router and each
  baseline; 95% percentile CIs.
- **McNemar's exact test** at the dev-selected operating point, on per-query
  correctness of the routed system (router vs TF-IDF+LR; A vs B).
- **Holm–Bonferroni** across the family {routers} × {pairs P-L, P-Q} ×
  {in-domain, 4 OOD folds} for each primary hypothesis.
- **Seed variance** is reported separately (5 seeds). A difference smaller than
  2 × seed-std is not called a win even if the bootstrap CI excludes 0.
- **Power caveat [E]:** at 20% test (~486 queries pooled, ~200 for MMLU-Pro), the
  per-dataset CIs on call rate are expected to be several points wide. Per-dataset
  results are therefore descriptive, and only the pooled test is confirmatory.

## 9. Success / failure criteria (decided before running) [P]

Stage 0 is **supportive of H1** only if, for pair P-L **or** P-Q, the best learned
router (B-s, B-m or A) satisfies **all** of:

1. CCR@−1 is lower than TF-IDF+LR by **≥ 5 percentage points** of call rate, with
   a Holm-adjusted 95% bootstrap CI excluding 0, pooled in-domain;
2. it beats random-at-matched-rate and the dataset-prior router on deferral AUC in
   **≥ 3 of 4** OOD folds;
3. ECE ≤ 0.10 in-domain and ≤ 0.15 averaged over OOD folds.

Stage 0 **falsifies H1** (for this pool) if no learned router meets criterion 1, or if
the dataset-prior router is within the CI of the best learned router in-domain
while the learned router fails criterion 2. The result would then repeat
LLMRouterBench's "ties a simple baseline" finding, and the paper would need a
different contribution (advisor options N2/N3 or a change of direction).

Stage 0 **supports H2** only if A is not worse than the best B by more than
2 points CCR@−1 (non-inferiority margin; one-sided 95% CI) **and** A beats B on at
least one pre-declared secondary (OOD ECE or train-size ablation at 10%). It
**falsifies H2** if B is non-inferior to A and A has ≥ 3× the p50 router latency
on the same host. The title's "Tiny-LM" (and any Jacobi component attached to it)
would then need to be dropped or justified differently.

The 5-point, 2-point, 0.10 and 0.15 thresholds are **our proposals**. They are not
taken from a source and the advisor should confirm or change them before Stage 0 runs.

## 11. Open questions and uncertainty

1. Whether `arenahard*` (judge-scored, {0, 0.5, 1}) should enter as a secondary
   soft-label pool. It is excluded from the primary analysis for now.
2. Whether LLMRouterBench's Qwen3-8B runs used thinking mode is **inferred** from
   completion length only. The paper/README configs should be checked before P-Q
   results are interpreted.
3. The Stage-0 pool is 7–9B → 235B. The manuscript's edge models (2–4B, and
   diffusion LMs) will have different headroom. Stage-0 conclusions about H2 transfer
   to them only as a hypothesis.
4. Query matching uses exact `origin_query` strings. Any prompt-format differences
   between the two settings' runs of the same dataset have not been audited.
5. Mix-or-Split (IEEE TPDS 2026) is still unread [S: d8 §7 item 1]. It may already
   contain the H3 comparison.
